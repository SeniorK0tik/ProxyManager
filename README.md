# Proxy Manager

Пускает трафик **выбранных приложений Windows** через SOCKS5 или HTTP-прокси, остальной трафик идёт напрямую. Похоже на Proxifier, написано на Rust.

- Правила для приложений: по имени файла (`chrome.exe`), полному пути или маске (`*\Telegram Desktop\*.exe`).
- Несколько прокси-профилей. Каждому правилу можно назначить свой прокси, «напрямую» или «блокировать».
- Поддерживаются SOCKS5 и HTTP CONNECT, оба с логином и паролем.
- Правила меняются на лету, без перезапуска.
- UDP проксируемых приложений блокируется, чтобы он не утёк мимо прокси. Браузеры при этом переходят с QUIC на TCP. DNS (порт 53) пропускается.
- Если прокси недоступен, соединение приложения сбрасывается, а не уходит напрямую.
- Графический интерфейс (egui): вкладки правил, прокси, запущенных процессов, активных соединений и журнала; иконка в трее; автозапуск при входе в Windows.
- Список исключений: LAN, loopback и multicast по умолчанию никогда не проксируются.

## Как это работает

```
 chrome.exe ──SYN──► WinDivert (outbound, !loopback)
                       │ локальный порт → PID → путь к exe → правило
                       ├─ напрямую   → пакет уходит без изменений
                       ├─ блокировка → пакет отбрасывается
                       └─ прокси     → пакет «отражается» на локальный relay
                                         ▼
                               relay (tokio) ── SOCKS5 / HTTP CONNECT ──► прокси ──► сервер
```

Перехват работает через драйвер [WinDivert](https://reqrypt.org/windivert.html). Исходящий пакет `L:p → R:443` от проксируемого приложения переписывается в `R:p → L:relay` и возвращается в стек как входящий. Relay принимает соединение и по адресу `R:p` находит в NAT-таблице исходное назначение `R:443`. Затем он открывает туннель через прокси. Ответные пакеты relay переписываются обратно, поэтому приложение думает, что общается с настоящим сервером. Владелец соединения определяется через `GetExtendedTcpTable`/`GetExtendedUdpTable`.

## Структура

| Крейт | Назначение |
|---|---|
| `crates/pm-core` | Кроссплатформенное ядро: конфиг, правила, разбор пакетов, NAT-движок, клиенты SOCKS5/HTTP, relay, статистика |
| `crates/pm-windows` | Windows: привязка к WinDivert (DLL загружается в рантайме), таблицы соединений, брандмауэр, UAC, автозапуск |
| `crates/pm-app` | Приложение: контроллер, GUI, трей |

## Установка

1. Скачайте `ProxyManager-vX.Y.Z-windows-x64.zip` со страницы [Releases](https://github.com/SeniorK0tik/ProxyManager/releases) и распакуйте.
2. Проверьте, что рядом с `proxy-manager.exe` лежат `WinDivert.dll` и `WinDivert64.sys`.
3. Запустите `proxy-manager.exe`. Программа попросит права администратора: без них WinDivert не работает.

При первом запуске перехвата программа добавляет правило брандмауэра Windows «Proxy Manager relay». Оно разрешает входящие соединения к relay.

## Использование

1. **Прокси**: добавьте сервер (тип, адрес, порт, при необходимости логин и пароль) и нажмите «Проверить».
2. **Правила**: создайте правило, выберите действие «Через прокси …» и добавьте приложения. Их можно ввести вручную, выбрать `.exe` или взять со вкладки «Процессы».
3. Нажмите **«Применить»**, затем **«Запустить»**.
4. Вкладка **«Соединения»** показывает, какие соединения идут через прокси и сколько данных передано.

Соединения, которые были открыты до запуска перехвата, не перенаправляются. Перезапустите приложение или дождитесь, пока оно переподключится.

Аргументы командной строки: `--config <файл>`, `--start` (сразу включить проксирование), `--minimized` (запуститься в трее), `--no-elevate`.

Конфиг хранится в `%APPDATA%\ProxyManager\config.toml`, логи — в `%APPDATA%\ProxyManager\logs`. Пример конфига: [`config.example.toml`](config.example.toml).

### Шаблоны приложений

| Шаблон | Что совпадает |
|---|---|
| `chrome.exe` | любой `chrome.exe` в любой папке |
| `C:\Program Files\App\app.exe` | только этот файл |
| `*\Telegram Desktop\*.exe` | любой `.exe` в папке `Telegram Desktop` |
| `game?.exe` | `game1.exe`, `game2.exe`, … |

Регистр не учитывается. Правила проверяются сверху вниз, срабатывает первое подходящее.

## Сборка

Нужен Rust 1.88+.

```powershell
# Windows
cargo build --release -p pm-app
./scripts/fetch-windivert.ps1 -Dest vendor/windivert   # WinDivert.dll + WinDivert64.sys
./scripts/package.ps1                                   # dist/ProxyManager-windows-x64.zip
```

Проверка из Linux (без линковки):

```bash
rustup target add x86_64-pc-windows-gnu
cargo clippy --workspace --all-targets --target x86_64-pc-windows-gnu
```

## Тесты и покрытие

```bash
cargo test --workspace                       # unit, интеграционные и headless-тесты GUI
cargo llvm-cov --workspace --summary-only    # покрытие
```

- `pm-core`: разбор пакетов, NAT-движок, правила, SOCKS5/HTTP (на скриптованных и mock-серверах), relay end-to-end через mock-прокси.
- `pm-windows`: разбор таблиц соединений, битовые поля `WINDIVERT_ADDRESS`, команды `netsh` и `schtasks`. На Windows дополнительно проверяются живые сокеты и определение процесса.
- `pm-app`: контроллер с фейковой платформой, а также GUI через [egui_kittest](https://crates.io/crates/egui_kittest): реальные виджеты и клики без окна.
- **E2E на реальном драйвере** (`crates/pm-app/tests/e2e_windows.rs`): `curl.exe` обращается к недоступному адресу `203.0.113.10` и получает ответ через mock-прокси. Тест проверяет SOCKS5, HTTP CONNECT, блокировку и смену правил на лету, а также что чужой трафик не затронут. Нужны права администратора:

  ```powershell
  $env:PM_WINDIVERT_DIR = "$PWD\vendor\windivert"
  cargo test -p pm-app --test e2e_windows -- --ignored --test-threads=1
  ```

CI (GitHub Actions) выполняет fmt, clippy (в том числе под Windows-таргет), тесты с покрытием (порог 90% строк) на Linux, а на Windows — тесты, e2e с WinDivert, сборку и упаковку zip. Релизы собирает отдельный workflow (см. «Релизы»).

## Релизы

История изменений ведётся в [`CHANGELOG.md`](CHANGELOG.md). Раздел версии становится описанием релиза.

Как выпустить новую версию:

1. Поднимите `version` в `[workspace.package]` корневого `Cargo.toml`.
2. Перенесите записи из `## [Unreleased]` в новый раздел `## [X.Y.Z] - ГГГГ-ММ-ДД` и добавьте ссылку внизу файла.
3. Закоммитьте изменения и отправьте тег:

   ```bash
   git tag vX.Y.Z
   git push origin main vX.Y.Z
   ```

Workflow **Release** проверяет, что версия тега совпадает с `Cargo.toml` и что для неё есть раздел в changelog. Затем он прогоняет тесты (включая e2e с WinDivert), собирает `ProxyManager-vX.Y.Z-windows-x64.zip` с файлом `.sha256` и публикует GitHub Release. Теги с дефисом (`v1.0.0-rc.1`) публикуются как pre-release. Пересобрать существующий тег можно вручную: Actions → Release → Run workflow.

## Ограничения

- Проксируется только TCP. UDP выбранных приложений блокируется или пропускается напрямую — это задаётся в настройках.
- DNS-запросы выполняет системная служба (Dnscache), поэтому имена разрешаются локально, а через прокси уходит IP-адрес.
- Некоторые античиты и антивирусы реагируют на драйвер WinDivert.
- Поддерживается только Windows x64.
